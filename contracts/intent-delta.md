# Intent-delta contract

An intent delta is a reviewable transition, never the accepted spec. A change may contain Markdown intent files under `specs/` or `deltas/<module-id>/spec.md`, but not both trees. Each begins with `# Intent delta: <spec-id>`; the account-delta layout requires the declared module id to match its path. The declared id, rather than the delta path, selects an accepted spec. The operation headings are `## Add term:`, `## Replace term:`, `## Add requirement:`, `## Replace requirement:`, `## Remove requirement:` and `## Remove scenario:`. Unknown operations fail closed. The accepted spec format remains [spec.md](spec.md).

`Add term` carries a non-empty free-form module vocabulary definition and projects it to `## Term: <term-id>`. An existing term with identical content is already applied; the same id with different content is rejected. Terms contribute to the affected Requirement definition fingerprints as described in the spec contract.

`Replace term` names an accepted `<term-id>` and carries `From: sha256:<digest>`, a non-empty `Because: <reason>`, a blank line and the complete non-empty target definition. The `From` digest identifies the exact accepted `## Term:` block. If accepted content no longer matches that digest or already carries the target definition, the operation is respectively stale or applied. A missing accepted term is rejected; there is no implicit term addition, rename or removal. A delta cannot both add and replace one term id.

Every Term participates in each Requirement definition fingerprint of its spec, so a planned term replacement changes the fingerprint of every Requirement in that module, including those the change does not replace. Their accepted Realization and Verification Review heads stop ratifying once the target is applied: validation reports the missing current review, and the change's own successor reviews ratify the target definition. The change is not required to replace those Requirements. `intent-preview` lists each such Requirement that declares a review and is neither replaced nor removed by the change as `successor review owed:`, so the obligation is visible before application rather than discovered at finalization. Term removal is not supported; a term no Requirement needs any longer can be rewritten by replacement.

`Add requirement` carries a complete Requirement block with optional `Title:`, `Realization:` and `Verification:` labels, a non-empty normative body and at least one `### Add scenario:` block. It creates a new spec at `<model-root>/<spec-id>/spec.md` if needed, or appends to an existing spec. An existing Requirement with the same id is applied only when its complete body, title, review declarations and ordered Scenarios match exactly; extra Scenarios are not ignored.

`Replace requirement` carries `From: sha256:<digest>`, `Because: <reason>`, optional `Title: <concise title>`, optional `Realization: reviewed`, optional `Verification: reviewed`, optional `Remove scenarios: <comma-separated-ids>`, a blank line, the complete target Requirement body and complete `### Scenario:` blocks. The target may add or rewrite Scenarios. Every accepted Scenario absent from the target must be declared in `Remove scenarios:`. The declaration must name no Scenario that remains. The `From` digest identifies the complete accepted Requirement Markdown block. If accepted content no longer matches that digest or already equals the target Requirement, the operation is respectively stale or applied.

`Remove requirement` and `Remove scenario` carry `From:` and `Because:` labels. `Remove scenario` names its stable `<scenario-id>` and fingerprints the accepted Scenario block; `Remove requirement` fingerprints the accepted Requirement and all its Scenarios. `Replaced-by:` may record the successor. A Scenario removal may not leave a Requirement without Scenarios. A Requirement removal that leaves no Requirements retires the spec file. Removal fails while the deleted identity has current workspace, `Realizes`, realization, verification or Verification Challenge references. History in archived changes is not rewritten.

A change of review rigor is an ordinary `Replace requirement` whose target carries the intended `Realization:` and `Verification:` labels; omitting a label in the target removes that declaration. Each change may address a Requirement only once, so overlapping operations require a revised complete delta. No operation infers a rename.

`azimuth change intent-capture` writes current `From` values for Requirement and Term replacement and for removal without changing accepted specs. It never overwrites a different existing value. `azimuth change intent-preview --out <file>` computes the exact target from accepted sources, displays the before/after spec text and stores a review snapshot. An existing preview file with different content is not overwritten. `azimuth change intent-apply --preview <file>` requires an active or accepted-and-complete change and compares that snapshot with a freshly computed projection. Mismatch or a stale `From` blocks application. `finalize` and `archive` never apply the delta; they require it to have been applied and the resulting model to validate.

The projection preserves unrelated accepted Requirement blocks and non-normative spec text. It validates every target spec with the accepted parser before any write. Multiple target files are staged before replacement, but filesystem replacement across several files is not a transaction; a failed replacement may require repair and a fresh preview.

## Topology for authoring commands

`intent-capture`, `intent-preview`, `intent-apply`, `account-capture`, `account-preview` and `account-apply` take no `--project` or `--workset`. An author fingerprints and projects blocks of the model held by the repository the command runs in and never has to observe other repositories. The commands resolve their topology from a project catalog or a local workspace as described in [project-catalog.md](project-catalog.md#local-loads-without-a-workset); the intent commands and `account-apply` load the complete current model with it. Assessing the complete federated account, including source linkage and support, remains `change validate --project <catalog> --workset <workset>`.

## Corrections after completion

A correction requested after CI/PR feedback is an explicitly related new change against the current model, which already includes any applied original delta. The `correction.json` scope/basis contract is defined in [validation.md](validation.md#explicit-correction-scope). It preserves the original archived change unchanged. Reconcile any changed accepted-block guards, author the correction's own transition and retain successor assessments for affected definitions/inputs. Do not reapply or silently mutate the original delta. Current semantic reviews, native execution and actual human acceptance still gate completion.
