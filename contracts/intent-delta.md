# Intent-delta contract

An intent delta is a reviewable transition, never the accepted spec. A change may contain one or more Markdown files under `specs/`; each begins with `# Intent delta: <spec-id>`. The declared id, rather than the delta path, selects an accepted spec. The operation headings are `## Add claim:`, `## Replace claim:`, `## Remove claim:`, `## Remove case:` and `## Change criticality:`. Unknown operations fail closed. The accepted spec format remains [spec.md](spec.md).

`Add claim` carries a complete Claim block with `Criticality:`, a non-empty normative body and at least one `### Add case:` block. It creates a new spec at `<model-root>/<spec-id>/spec.md` if needed, or appends to an existing spec. An existing Claim with the same id is applied only when its complete body, criticality and ordered Cases match exactly; extra Cases are not ignored.

`Replace claim` carries `From: sha256:<digest>`, `Because: <reason>`, `Criticality: <level>`, optional `Remove cases: <comma-separated-ids>`, a blank line, the complete target Claim body and complete `### Case:` blocks. The target may add or rewrite Cases. Every accepted Case absent from the target must be declared in `Remove cases:`. The declaration must name no Case that remains. The `From` digest identifies the complete accepted Claim Markdown block. If accepted content no longer matches that digest or already equals the target Claim, the operation is respectively stale or applied.

`Remove claim` and `Remove case` carry `From:` and `Because:` labels. `Remove case` names its stable `<case-id>` and fingerprints the accepted Case block; `Remove claim` fingerprints the accepted Claim and all its Cases. `Replaced-by:` may record the successor. A Case removal may not leave a Claim without Cases. A Claim removal that leaves no Claims retires the spec file. Removal fails while the deleted identity has current workspace, realization, design, verification or challenge-plan references. History in archived changes is not rewritten.

`Change criticality` retains `From:`, `To:`, `Because:` and the existing lowering `Revisit:` rule. Each change may address a Claim only once, so overlapping operations require a revised complete delta. No operation infers a rename.

`azimuth change intent-capture` writes current `From` values for replacement and removal without changing accepted specs. It never overwrites a different existing value. `azimuth change intent-preview --out <file>` computes the exact target from accepted sources, displays the before/after spec text and stores a review snapshot. An existing preview file with different content is not overwritten. `azimuth change intent-apply --preview <file>` requires an active or accepted-and-complete change and compares that snapshot with a freshly computed projection. Mismatch or a stale `From` blocks application. `finalize` and `archive` never apply the delta; they require it to have been applied and the resulting model to validate.

The projection preserves unrelated accepted Claim blocks and non-normative spec text. It validates every target spec with the accepted parser before any write. Multiple target files are staged before replacement, but filesystem replacement across several files is not a transaction; a failed replacement may require repair and a fresh preview.
