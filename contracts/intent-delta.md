# Intent-delta contract

An intent delta is a reviewable transition, never the accepted spec. A change may contain Markdown intent files under `specs/` or `deltas/<module-id>/spec.md`, but not both trees. Each begins with `# Intent delta: <spec-id>`; the account-delta layout requires the declared module id to match its path. The declared id, rather than the delta path, selects an accepted spec. The operation headings are `## Add term:`, `## Replace term:`, `## Add requirement:`, `## Replace requirement:`, `## Remove requirement:` and `## Remove scenario:`. Unknown operations fail closed. The accepted spec format remains [spec.md](spec.md).

`Add term` carries a non-empty free-form module vocabulary definition and projects it to `## Term: <term-id>`. An existing term with identical content is already applied; the same id with different content is rejected. Terms contribute to the affected Requirement definition fingerprints as described in the spec contract.

`Replace term` names an accepted `<term-id>` and carries `From: sha256:<digest>`, a non-empty `Because: <reason>`, a blank line and the complete non-empty target definition. The `From` digest identifies the exact accepted `## Term:` block. If accepted content no longer matches that digest or already carries the target definition, the operation is respectively stale or applied. A missing accepted term is rejected; there is no implicit term addition, rename or removal. A delta cannot both add and replace one term id.

Every Term participates in each Requirement definition fingerprint of its spec, so a planned term replacement changes the fingerprint of every Requirement in that module, including those the change does not replace. Their accepted Realization and Verification Review heads stop ratifying once the target is applied: validation reports the missing current review, and the change's own successor reviews ratify the target definition. The change is not required to replace those Requirements. `intent-preview` lists each such Requirement that declares a review and is neither replaced nor removed by the change as `successor review owed:`, so the obligation is visible before application rather than discovered at finalization. Term removal is not supported; a term no Requirement needs any longer can be rewritten by replacement.

`Add requirement` carries a complete Requirement block with optional `Title:`, `Realization:` and `Verification:` labels, a non-empty normative body and at least one `### Add scenario:` block. It creates a new spec at `<model-root>/<spec-id>/spec.md` if needed, or appends to an existing spec. An existing Requirement with the same id is applied only when its complete body, title, review declarations and ordered Scenarios match exactly; extra Scenarios are not ignored.

`Replace requirement` carries `From: sha256:<digest>`, `Because: <reason>`, optional `Title: <concise title>`, optional `Realization: reviewed`, optional `Verification: reviewed`, optional `Remove scenarios: <comma-separated-ids>`, a blank line, the complete target Requirement body and complete `### Scenario:` blocks. The target may add or rewrite Scenarios. Every accepted Scenario absent from the target must be declared in `Remove scenarios:`. The declaration must name no Scenario that remains. The `From` digest identifies the complete accepted Requirement Markdown block. If accepted content no longer matches that digest or already equals the target Requirement, the operation is respectively stale or applied.

`Remove requirement` and `Remove scenario` carry `From:` and `Because:` labels. `Remove scenario` names its stable `<scenario-id>` and fingerprints the accepted Scenario block; `Remove requirement` fingerprints the accepted Requirement and all its Scenarios. `Replaced-by:` may record the successor. A Scenario removal may not leave a Requirement without Scenarios. A Requirement removal that leaves no Requirements retires the spec file. History in archived changes is not rewritten.

### References to a removed identity

A removed Requirement or Scenario may still be referenced by realization declarations (Requirement and Scenario realizations and a mechanism's Scenario relevance), verification declarations (Requirement and Scenario verifications, Scenario-owned elements, Check bindings and Verification Challenge Requirement scope), account support, workspace realization obligations or code `Realizes` sites. An identity that the same delta retains elsewhere is not removed. The workflow reviews the spec delta before the realization and verification deltas that repair these references are authored, and implementation repairs `Realizes` sites, so the references are staged:

- **Owed while authoring.** `change validate`, `intent-preview` and `change status` still project the delta. `change validate` checks every removal against the prospective account, which composes this change's realization and verification deltas with the current model and supplied linkage and support, and reports each identity that is still referenced as one `removed-identity-referenced` error ([findings.md](findings.md)) at the removal operation. Its detail names the removed identity and every referencing location with the facet that owes the repair: realization delta, verification delta, support, code Realizes site or workspace declaration. A reference that the change's own deltas remove no longer counts, so the finding clears once they repair it. Dangling-declaration findings at those same locations are not reported a second time. The Check bindings of removed Scenarios do not refuse the prospective load, so the rest of validation still runs; any other load failure still does. `intent-preview` writes the preview unchanged and lists each removal that the accepted account still references on standard error as `owed reference repair:`. The preview file holds only the spec target that `intent-apply` compares, so a snapshot reviewed while repairs were owed stays valid once they are made.
- **Refused at application.** `intent-apply` and `archive` fail while the accepted account or linkage still references a removed identity. `finalize` applies the change's pending intent and account deltas together and fails while the composed account or linkage still references one (see [Combined application at finalize](#combined-application-at-finalize)). A dangling reference never enters the accepted model.

A change of review rigor is an ordinary `Replace requirement` whose target carries the intended `Realization:` and `Verification:` labels; omitting a label in the target removes that declaration. Each change may address a Requirement only once, so overlapping operations require a revised complete delta. No operation infers a rename.

`azimuth change intent-capture` writes current `From` values for Requirement and Term replacement and for removal without changing accepted specs. It never overwrites a different existing value. `azimuth change intent-preview --out <file>` computes the exact target from accepted sources, displays the before/after spec text and stores a review snapshot; owed reference repairs go to standard error, not into the snapshot. An existing preview file with different content is not overwritten. `azimuth change intent-apply --preview <file>` requires an active or accepted-and-complete change and compares that snapshot with a freshly computed projection. Mismatch or a stale `From` blocks application. `archive` never applies the delta; it requires it to have been applied and the resulting model to validate. `finalize` applies it only together with the change's pending account deltas, as described below.

The projection preserves unrelated accepted Requirement blocks and non-normative spec text. It validates every target spec with the accepted parser before any write. Multiple target files are staged before replacement, but filesystem replacement across several files is not a transaction; a failed replacement may require repair and a fresh preview.

### Combined application at finalize

A rename cannot be applied one facet at a time. `intent-apply` refuses to remove a Scenario that the accepted verification still binds, and `account-apply` refuses to bind a Check to the successor Scenario that the accepted spec does not yet declare. `azimuth change finalize <change> [--preview <intent-preview>] [--account-preview <account-preview>]` therefore applies whatever the change has not applied yet as one staged operation:

1. It projects the intent delta and the account deltas against the accepted model. With nothing pending it takes no preview and finalizes the accepted model as before. A pending intent delta requires `--preview` with the reviewed `intent-preview` snapshot, and pending account deltas require `--account-preview` with the reviewed `account-preview` snapshot. Each must equal a fresh projection byte for byte; a stale snapshot is refused with the same message as `intent-apply` or `account-apply`. A preview supplied for a facet that is already applied is an error. As with the individual apply commands, the change must be active with `Status: active` or `Status: accepted and complete`.
2. It composes both projections onto a temporary copy of the accepted model and loads that composition with the same topology, linkage and support as the accepted load. Every planned removal is checked against the composed account: an identity that is still referenced after the change's own deltas is reported as `removed-identity-referenced` at the removal, naming each remaining location and the facet that owes it, and finalize fails. Only references that remain in the composed result are refused; references the change's deltas repair are not.
3. It runs every finalization gate against the composition: completion obligations, acceptance and ratification, the assurance snapshot when supplied, and an accepted-state model without errors or warnings.
4. Only a composition that passes is written. Each target is staged beside itself and re-read against the content it was projected from; any difference refuses before anything is replaced. Spec, realization and verification targets are then replaced and retired specs removed. The written model is reloaded and checked again, review heads and `finalization.json` are written from it, and Work Provenance is exported. If a replacement or the recheck fails, finalize restores the accepted bytes of every facet it replaced.

On any refusal the accepted model, the change and its finalization receipt are left exactly as they were. `intent-apply` and `account-apply` are unchanged and remain the way to apply a facet whose references the accepted account does not block.

## Topology for authoring commands

`intent-capture`, `intent-preview`, `intent-apply`, `account-capture`, `account-preview` and `account-apply` take no `--project` or `--workset`. An author fingerprints and projects blocks of the model held by the repository the command runs in and never has to observe other repositories. The commands resolve their topology from a project catalog or a local workspace as described in [project-catalog.md](project-catalog.md#local-loads-without-a-workset); the intent commands and `account-apply` load the complete current model with it. Assessing the complete federated account, including source linkage and support, remains `change validate --project <catalog> --workset <workset>`.

## Corrections after completion

A correction requested after CI/PR feedback is an explicitly related new change against the current model, which already includes any applied original delta. The `correction.json` scope/basis contract is defined in [validation.md](validation.md#explicit-correction-scope). It preserves the original archived change unchanged. Reconcile any changed accepted-block guards, author the correction's own transition and retain successor assessments for affected definitions/inputs. Do not reapply or silently mutate the original delta. Current semantic reviews, native execution and actual human acceptance still gate completion.
