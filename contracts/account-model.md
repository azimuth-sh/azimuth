# Requirement-first account inspection (candidate)

`account_model::inspect_with_support(model_root, workspace, manifests, support_manifests)` assembles the current or projected module documents for structural inspection. It reads `spec.md`, `realization.md` and `verification.md` under the supplied model root, with workspace Area declarations and existing extracted manifests. The model root may be a temporary projection; the inspector does not apply or archive a change.

Parse failures, duplicate facet authority, unknown Requirement or Area references, invalid review Scenarios/references and any purported accepted review state return file/line diagnostics and block application. Missing source participation, missing account scopes and pending review remain report findings. The report counts loaded facets and lists deterministic unresolved findings. It is not a review or Assurance State. In particular, a document declaration, a `Realizes` tag or a Check implementation alone cannot establish a Requirement.

For each Requirement realization, inspection resolves the matching spec Requirement and its behavioral domain. `Areas:` must name declared workspace Areas, and every listed Area must contain an extracted `Realizes` site for that Requirement. A source identity's Area is preferred; otherwise the workspace mount resolves the site's file. This is a participation floor only. Element Areas are checked for declaration. Scenario realization declarations explicitly resolve to Scenarios under their enclosing Requirement; unknown Scenarios are hard structural errors. A selected Mechanism declares applicability using stable project-wide Scenario IDs. Module and parent membership do not reconstruct identities; duplicate references are rejected. Unknown Scenario references are hard structural errors; an omitted scope remains unspecified rather than inferred from nesting. The list does not satisfy Scenario-to-Check contribution requirements. A selected Mechanism without an extracted implementation is reported unresolved; several distinct sites may support one Mechanism, but their adequacy and completeness remain unjudged.

For each verification Requirement, inspection resolves the matching spec Requirement. The verification parser derives required Elements from Requirement nesting and checks optional explicit references to shared Elements. Optional Scenario verification declarations normalize to full Scenario identities and must resolve to Scenarios under the enclosing Requirement; unknown Scenarios are hard structural errors. Explanatory Sections require no inventory. Scenario verification prose and nested Element participation never satisfy Check contribution requirements. A separate extracted account-support manifest may provide fingerprinted source/configuration Artifact support for a required Element and an explicit Check-to-Scenario contribution. Without those exact records, the inspector reports the relationship unresolved. A Check with no Scenario contribution is reported as an orphan; support-only Elements remain valid without Checks. One Check may contribute to Scenarios under several Requirements when each Requirement has Element support and each contribution is explicit. The existing `check_implementations` manifest entry names a Check but does not identify a Scenario contribution; a matching string or count cannot discharge coverage. Even a resolved structural contribution is not execution evidence or a positive review.

`judgments.md` is not read. Independent review state is not part of the account documents: Verification and Realization Reviews are sealed records retained by changes, and the model carries only the review heads that `azimuth change finalize` writes ([assurance-reviews.md](assurance-reviews.md)).

A Requirement that declares `Verification:` without a Requirement verification scope produces a finding when a module participates in this account format; a Requirement realization is never required. A `realization.md` in the entry format and a flat `verification.md` are not read by this inspector; a module enters it when it uses Requirement-first headings. Empty manifests leave realization and verification support visibly unresolved. Existing Run results and deployed Verification Targets are not read. Model validation and review-dependency fingerprints retain the assembled account; durable Assurance State is computed separately.

The three-argument `inspect(model_root, workspace, manifests)` wrapper passes an empty support set for compatibility and therefore leaves Element and Scenario support unresolved. Source/configuration support is read only from explicit `AccountSupport` records; core never analyzes implementation files.

Requirement realization, verification and review headings name stable Requirement ids. Scenario realizations remain optional explanations and cannot discharge Check contribution requirements. 

Document-authored candidate Checks own their Method, Terminal and Scenario meaning. Inspection rejects duplicate semantic authority against source-owned Checks and resolves Scenario/Mechanism references. Source support joins through existing check_implementations records after workspace identity assembly; absent or unstable implementation leaves Check and Scenario participation unresolved. Normal model loading validates the same authority rules and recognizes candidate Check implementations without inventing Evidence Bindings. Cross-Requirement normalized relationships, rationale and implementation fingerprints participate in candidate review digests.
