# Claim-first account inspection (candidate)

`account_model::inspect_with_support(model_root, workspace, manifests, support_manifests)` assembles the current or projected module documents for structural inspection. It reads `spec.md`, `design.md`, `verification.md` and `judgments.md` under the supplied model root, with workspace Area declarations and existing extracted manifests. The model root may be a temporary projection; the inspector does not apply or archive a change.

Parse failures, duplicate facet authority, unknown Claim or Area references, invalid review Cases/references and any purported accepted review state return file/line diagnostics and block application. Missing source participation, missing account scopes and pending review remain report findings. The report counts loaded facets and lists deterministic unresolved findings. It is not a Claim Judgment or Assurance State. In particular, a document declaration, a `Realizes` tag or a Check implementation alone cannot establish a Claim.

For each design Claim, inspection resolves the matching spec Claim and its non-routine behavioral criticality. `Areas:` must name declared workspace Areas, and every listed Area must contain an extracted `Realizes` site for that Claim. A source identity's Area is preferred; otherwise the workspace mount resolves the site's file. This is a participation floor only. Element Areas are checked for declaration. Case design declarations explicitly resolve to Cases under their enclosing Claim; unknown Cases are hard structural errors. A selected Mechanism declares applicability using stable project-wide Case IDs. Module and parent membership do not reconstruct identities; duplicate references are rejected. Unknown Case references are hard structural errors; an omitted scope remains unspecified rather than inferred from nesting. The list does not satisfy Case-to-Check contribution requirements. A selected Mechanism without an extracted implementation is reported unresolved; several distinct sites may support one Mechanism, but their adequacy and completeness remain unjudged.

For each verification Claim, inspection resolves the matching spec Claim. The verification parser derives required Elements from Claim nesting and checks optional explicit references to shared Elements. Optional Case verification declarations normalize to full Case identities and must resolve to Cases under the enclosing Claim; unknown Cases are hard structural errors. Explanatory Sections require no inventory. Case verification prose and nested Element participation never satisfy Check contribution requirements. A separate extracted account-support manifest may provide fingerprinted source/configuration Artifact support for a required Element and an explicit Check-to-Case contribution. Without those exact records, the inspector reports the relationship unresolved. A Check with no Case contribution is reported as an orphan; support-only Elements remain valid without Checks. One Check may contribute to Cases under several Claims when each Claim has Element support and each contribution is explicit. The existing `check_implementations` manifest entry names a Check but does not identify a Case contribution; a matching string or count cannot discharge coverage. Even a resolved structural contribution is not qualification, execution evidence or a positive Judgment.

`judgments.md` permits `## Section:` prose and `## Claim review: <claim-id>` declarations. Every Claim review must declare `State: pending`, exactly its current Cases, and Design and Verification references to the same Claim. Any accepted state is a parse error: a projected draft cannot manufacture a verdict. The report still marks every valid review pending. There is no finished review representation in this slice.

Missing non-routine Claim design, verification or review scopes produce findings when a module participates in this account format. Legacy `design.md` and flat `verification.md` facets are skipped during mixed adoption; a module enters this inspector when it uses Claim-first headings. Legacy modules without these facets are outside this inspector's migration scope. Empty manifests leave realization and verification support visibly unresolved. Existing Run results, policy decisions, and deployed subjects are not read. Current model validation and review-dependency fingerprints retain the assembled account; source-authored verification extraction, accepted Claim-first Judgment and Challenge integration and durable Assurance State remain separate work.

The three-argument `inspect(model_root, workspace, manifests)` wrapper passes an empty support set for compatibility and therefore leaves Element and Case support unresolved. Source/configuration support is read only from explicit `AccountSupport` records; core never analyzes implementation files.

Claim design, verification and review headings use local Claim ids under their declared module. Parsed account records carry qualified identities. Case designs remain optional explanations and cannot discharge Check contribution requirements. A shared Mechanism outside a Claim cannot use an unqualified Case name.

Document-authored candidate Checks own their Method, Terminal and Case meaning. Inspection rejects duplicate semantic authority against legacy and source-owned Checks and resolves Case/Mechanism references. Source support joins through existing check_implementations records after workspace identity assembly; absent or unstable implementation leaves Check and Case participation unresolved. Normal model loading validates the same authority rules and recognizes candidate Check implementations without inventing legacy Evidence Bindings. Cross-Claim normalized relationships, rationale and implementation fingerprints participate in candidate review digests.
