# Runtime target observations

Implementation contract for the approved runtime-observation-identity adjustment.

Collectors POST exactly `{observation}` to `/v1/projects/{project}/target-observations` with a scoped producer or publisher credential for Checks, and a scoped publisher credential for contexts. GET on that route provides bounded authenticated retained observations and resolution diagnostics. Receipt is `{fingerprint,replayed}` hashing canonical submitted observation, never server-enriched content. Replays keep original receipt time and attribution. Same source/execution with differing bytes is a conflict. Raw observations and resolution links use typed relational storage; no opaque JSON data columns.

Observation has exactly `format:"azimuth-target-observation", version:2, kind:"check"|"context", source, execution_id, environment, started_at_ms, finished_at_ms, targets, check, capture`. source/execution/environment are nonempty bounded identifiers. Times are UTC integer milliseconds, ordered, not future-dated. targets is a bounded unique list of `{component,image,instance}` where image is immutable `repository@sha256:...`, instance is an actual runtime process/container ID. These are measured identities, never inferred from release name, desired image, arrival time or whichever deployment is current. No Verification Target, release, or deployment binding is submitted. Empty targets retain inconclusive collection facts without attributing them to any deployment.

For kind check, capture is null and check is `{definition,outcome,details}`. The check payload is a raw Observation of one measurement; ASS normalizes it into a Run whose result is a Check Result. definition is the stable Verification-Target-free native import definition `{plan,adapters,routes}` from the existing one-Check/one-unit import launch ([`azimuth-run-launch-plan`](run-launch-plan.md) version 2 shape), with plan.fingerprint removed (it depends on the Verification Target). Preserve current exact Check/Scenario/implementation and provider fingerprints and `required_execution_context`; plan model identity remains as originally planned. ASS computes a new native plan/launch fingerprint only after mapping a target observation. Details is bounded nonsecret text retaining native measurement detail. Outcome is violated or inconclusive for exposure probes. No blind outcome promotion; unsupported support mappings remain rejected. Check definition changes require configuration updates, ordinary releases do not.

For kind context, check is null; capture is `{component,instance,started_at_ms,finished_at_ms,before,after}` with native Execution Context snapshot fields whose reports are `azimuth-execution-context` version 2. Both snapshots have identical runtime instance/boot identity and stable allowlisted reports. Exactly one corresponding target must exist. Context contracts are supplied as explicit local full reviewed contracts in collector configuration; no ASS read is needed. ASS validates against its independently registered contracts and preserves submitted bytes before deriving a deployment capture.

ASS resolves using retained complete reconciler observations around the measurement interval. It requires exact environment/component/digest/process identity and an unambiguous deployment with complete inventory; never just latest release. Both interval boundaries must be covered by independent complete observations of that same deployment/instance inventory, with no intervening conflicting/non-complete observation. Missing after-boundary reconciliation leaves evidence pending for later retry; delayed delivery can resolve historically. Rollback reuses images but has distinct deployment rollout identity, so image identity alone cannot resolve ambiguity. Counterexamples may cover a subset of one component's independently observed instance set; positive support would require full reviewed coverage and is not introduced here.

Resolution preserves immutable raw evidence and records the deployment Verification Target, raw fingerprint and reconciler observation fingerprints as accountable provenance. ASS may materialize native import Runs and deployment captures after resolution; server-side normalization is explicit and natively verified. Unresolved records are retained and visible, not discarded or attached to another release. Assessment/reconciliation retries pending resolution so publication order does not determine applicability. Existing native Run/capture ingestion remains supported as its own protocol, with unchanged historical meaning.

## Resolver provenance and storage

Materialized Runs identify the built-in `assurance-target-observations` normalizer, with formal native adapter, descriptor, configuration and capability fingerprints derived from the executing ASS binary and compiled resolver/native protocol source identities. ASS retains this descriptor relationally; authenticated GET `/v1/projects/{project}/target-normalizers` exposes the accountable identities. The configured upstream provider definition remains immutable in the original target observation and is separately referenced; it is not misrepresented as the code that performed server-side normalization. Run generation time is the actual normalization time, distinct from measurement start/finish.

Resolution attempts isolate semantic incompatibilities per observation. A malformed historical Verification Target or unsupported mapping remains pending with a diagnostic and cannot block unrelated evidence. Database/infrastructure failures remain failures. Processing is bounded and pending attempts rotate so permanently unmatched observations cannot starve newer facts.

Target observations, resolution links and normalizer descriptors are typed relational storage in ASS storage version 6, which initializes only a fresh, empty database and refuses any other schema signature (see [deployment Requirement Status](deployment-requirement-status.md#storage-rollout)). Version 1 target observations are not accepted; producers move to version 2 together with ASS. Do not roll back the binary alone; recovery is re-initialization and republication.

For kind context, the contract named by a capture is the component's derived contract: `contracts` in the collector configuration are keyed by component id, a report holds exactly one context named by that id, and its dotted leaf names are the keys of `values` ([deployment-requirement-status.md](deployment-requirement-status.md)). The service rejects a capture whose key set differs from the registered contract.
