# Challenge planning conformance

This self-contained synthetic experiment exercises repository decision use and semantic Challenge planning through public `azimuth` commands. It owns a standard Claim with a current Qualification and Claim Judgment, one claim-specific analyzer enrolled as a Check, mutation and broad-analysis Challengers, a distinct fault-injection Challenger and capability, all seven selector forms, an exact workspace, one linkage manifest and a short-lived standard-library adapter.

The gate proves that a surviving mutant is a `findings` Challenge Result, a fully killed mutant set is `clean`, and zero generated mutants or skipped tests are `inconclusive`. A fault activity may be shared by one Check attempt and one Qualification Challenge attempt, while their Observation and Challenge Result remain distinct records. Mutation, analyzer and fault modes emit only their own native outcome codes. The claim-specific analyzer produces an Observation; the broad analyzer produces a Claim Judgment Challenge Result.

The gate also checks each exact selector relation, target and fingerprint, route-local scope and accountable launch input, broad composition, required-form, candidate-cap, Qualification-context and cross-form failures. An isolated authored selector proves that zero resolution is a planning error distinct from a zero-mutant result. Scheduled omission retains gate work, import provenance echoes the exact staged id, digest and size, and selection drift preserves caller-owned output. It invokes `validate`, `export`, `adapter verify`, `run plan`, `run execute`, `run import`, `run verify` and `run inspect` only.

This is conformance evidence, not a provider service. The adapter is a fresh bounded process for each exchange. The experiment creates no ledger, ingest command, assurance state, daemon, cache or durable provider state; a clean Challenge Result is not product evidence and does not qualify a Claim.
