# Coordinate work packages

1. Read the target repository's instructions and complete approved change.
2. Run `azimuth change work-packages <id>`. Stop on unknown dependencies, cycles, overlapping or escaping owned paths, invalid status or missing objectives.
3. Keep shared contracts, proposal state, current-facet integration, outcome and archival paths under coordinator ownership.
4. Select only eligible packages. Generate each worker handoff with `azimuth change brief <id> --package <package>`.
5. Delegate only when the available agent runtime supports it. Otherwise execute packages sequentially using the same ownership boundary.
6. Require each worker to edit only declared paths and report files, permitted checks, results and residuals. Workers never finalize or archive.
7. Inspect returned diffs before marking package progress. Resolve integration work centrally and re-run package eligibility after every completion.
8. When all packages are integrated, return to `azimuth-apply` for current-facet updates and final readiness checks.

## Standard change workflow selection

Select `azimuth workflow init --workflow change-development --inputs <file> --instance <file> --repositories <file>` for ordinary change coordination. Inspect `azimuth workflow definition --workflow change-development` and `azimuth reference show workflow` for the exact input and inventory contracts. Supply explicit project/change identities, original request, optional referenced task instructions and declared module inventory; do not manually compose a process DAG or invent context-specific action names. Instruction overrides can direct retained-artifact copying while preserving approval and independent review gates.

Read `workflow next` using the same explicit repository map (or selected `--project`); handoffs carry portable references plus complete local execution locations. Act on `action` and typed `target`, and author one compact result (`work`, optional `target`, `outcome`, optional `report`, `outputs`). Pass the captured handoff, actual actor and current revision to `workflow update`; Azimuth derives identities, fingerprints and dependencies. `--actor` names one execution instance — a session, a subagent run or a person — never a role, attempt number or model; those are carried by the action, the attempt id and the descriptor. An installed agent integration's hook records the executing agent itself; run `workflow update` as one plain command and do not pass `--descriptor`. Without a hook, when the harness or orchestrator can state the executing agent, pass `--descriptor <file>` (an `azimuth-agent-descriptor` whose fields are each marked `harness`, `declared` or `unknown`); never guess a value, and omit the flag rather than invent one. Read `azimuth reference show work-provenance`. To restart a broken instance, `workflow abandon` it with a reason, keep the file inside the change's `.azimuth/`, and `workflow init --predecessor <that file>` a fresh one; never delete or rewrite earlier instances. Reuse the result as the report instead of writing duplicate wrapper files. The harness chooses workers and obtains real permission. A local approval label grants no permission itself.

After structural validation, prepare the complete local candidate authority and snapshot. Azimuth derives targets automatically. Independently review each non-routine Requirement definition, Scenarios, realization and verification through Requirement Review; no execution Verification Target belongs to that review. Execute Checks against explicitly selected exact Verification Targets, and run declared machine Verification Challenges against exact current assessments with resolved source scope. Publish actual Runs and effective context captures. The deployment assessor computes Requirement Status from current Requirement Review, exact release lineage, observed deployment composition, applicable evidence and fresh monitoring; do not author a separate positive status record. Different Verification Targets are joined only through those validated applicability relations. Keep local iterations local; publish the relied-on review and execution package from CI or another authorized boundary. Preserve adverse facts and reassessments; clean Challenge Results never establish support.
