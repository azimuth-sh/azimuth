# Outcome and finalization reference

`outcome.md` is authored with `Status: complete` and records what the completed change actually established: delivered behavior against completion conditions, accepted departures from proposal and change design, engineering verification, unperformed checks, residual risks and pending operational conditions. Source completion, release, deployment and observed behavior are distinct facts.

Do not manufacture production exposure, observations, approval or evidence. If outcome writing discovers a material unresolved obligation, return to the owning task and decision. A catch-all verify-change task does not replace complete artifact/execution contracts.

The human acceptance task records an actual accountable decision against the exact completed basis in separate durable `change-acceptance.json`, pinning candidate authority, exact outcome bytes and verified retained-input manifest. It does not edit the outcome after acceptance. Existing historical `Status: accepted` outcomes preserve their meaning; new workflow finalization requires the separate current decision. Use the installed acceptance record grammar; an agent never writes a favorable decision on its own initiative. Applicable Requirements that declare `Verification:` need current accepted sealed Verification Reviews, those that declare `Realization:` need current accepted sealed Realization Reviews, and both need the installed ratification basis. An acceptance record alone supplies no review, Run or deployment Requirement Status and waives no unrelated finding.

`finalize-change` combines model application, finalization and archival under one authorized workflow task. Apply reviewed spec and realization/verification deltas through their projectors when still pending. Finalization writes the latest ratifying review of each kind into the model's `verification-review.md` and `realization-review.md` from the change's sealed reviews. A stale preview or accepted-block guard requires reconciliation, not forced application. Validate the complete account, review/execution dependency closure, real acceptance, current finalization and generated provenance before archival. `change finalize` and `change archive` remain separate CLI operations, not separate mandatory workflow tasks.

Generated completion/provenance artifacts need an explicit closure boundary so they do not recursively invalidate the reviewed semantic candidate. Archive relocation must preserve portable references. Required records must remain recoverable from the submitted revision and declared storage; local scratch file presence alone is not durable retention. Finalization validates resulting artifacts and cannot treat an old passing command as evidence for changed behavior.

Keep archived records immutable. If Dima explicitly requests a correction after CI/PR feedback, create a related correction change against the current account, preserve the original record, and retain required successor reviews/acceptance for affected obligations. A correction before merge can join the existing PR; after merge it uses a new PR. Never double-apply the original delta.

Local completion does not commit, merge, publish or deploy. CI separately validates the submitted/integration candidate, assembles publication inputs deterministically and retains diagnostics for manual correction. No agent publication-input task or automatic CI work-package output is required.
