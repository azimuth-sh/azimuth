# Verification-delta reference

Verification is a guarded change facet symmetric with spec and design. Author `deltas/<module-id>/verification.md` against the accepted baseline after the spec and design deltas have independent accepted reviews. Its header is `# Verification delta: <module-id>`; use the installed account-delta operations and exact parent/baseline guards. Capture with `account-capture`, inspect `account-preview` and validate the complete prospective account. Parser success does not establish method adequacy.

The canonical grammar is `contracts/account-delta.md`, `contracts/account-verification.md` and applicable package contracts in the Azimuth repository. Use only forms supported by the installed release. Stable Requirement, Scenario, Mechanism, Check and Verification Challenge IDs have typed namespaces; module membership and authored parent relationships do not create aliases.

## Checks and packages

Routine Requirements owe no enrolled Checks or independent evidence review. Ordinary engineering tests enter the evidence graph only when deliberately enrolled.

A Check declares a method with observations, assertions, independently fixed expectations, controls, relevant boundary, finite selection and inconclusive conditions. Inline Check–Scenario contributions state what each observation establishes; a narrow contribution does not claim the whole Requirement. The combined contributions must cover the required propositions. Shared enforcement or another explicit relationship justifies representative coverage.

Source markers link implementations; they do not author applicability, judgments or approval. Package declarations are explicit. `azimuth.surface` supplies Surfaces and independent Expectation Sets; `azimuth.network` supplies Probes and origins. Publish field names rather than duplicating language types. Pin expectation data and relevant context definitions so their changes affect the right dependencies. `azimuth surface verify` checks descriptors, enumeration and joins, not behavior.

Required fixtures, positive/negative controls, measurement capture, native results and missing-data handling belong in the implemented method. A passing engineering command without its required capture is incomplete execution. Selected-test inventories, skips, unit coverage and actual context must remain inspectable; `whole` is one execution unit, not proof of complete internal coverage.

## Implementation-directed Challenges

Challenges examine production implementation and Checks. Declare the search purpose/form, selected Requirements or Mechanisms, Check relationships, exact examined inputs, tool configuration, controls, scope limits and exclusions. Mutation targets, build dependencies and exercised Checks are distinct scopes. Native target/scope records come from the installed execution contract; do not fabricate an accepted Requirement Review as a prerequisite or invent target fields.

Execute required Checks first. Failed Checks block Challenges and Requirement Review. Then execute affected Challenges against exact current implementation/Check inputs. Preserve native `clean | findings | inconclusive` outcomes: clean is a bounded no-objection result, not positive Requirement Status. Execution gaps and confirmed defects return to diagnosis/correction before review. An explicitly justified equivalence or irrelevance disposition remains a proposal for independent Requirement Review; never relabel findings as clean.

The Verification Challenge `Requirements` selector names product Requirements. A Check's nested Execution `Requirements` list names execution facilities. Do not confuse either with the required execution environment or inferred source scope. Tool adapters resolve emitted semantic sites to supported filters and retain exclusions, expansions and gaps. Core does not guess language semantics or silently broaden to a different capability.

## Execution and review

Use configured bounded `azimuth run plan`/`run execute` or import operations and validate actual native records. Deterministic tooling selects affected execution and gives the basis for omissions; selection is not an agent judgment. Exact target capture, required context and unit inputs constrain applicability. Existing hermetic-unit reuse remains a separate explicit contract; model revision equality alone does not transfer evidence.

Independent Requirement Review examines the complete implemented account, current execution records and Challenge dispositions after required local execution. Reviews retain their own definition/input basis; execution facts are not a substitute for adequacy or implementation assessment. Relevant corrections require affected execution and independent reassessment, while unrelated current records remain usable under native currentness rules.

Source/artifact Checks execute in their applicable local or CI environment. Deployment-only Checks and Monitors remain hosted obligations after authorized rollout. AAS computes deployment Requirement Status from reviewed definitions, lineage, observed composition, applicable evidence and fresh compatible context. No local Run, clean Challenge or reviewer decision alone confirms deployment behavior. Requirement Status is not authored.

## Retention and publication

Retain reviewer-authored Markdown, sealed native reviews, relied-on Runs, scope/capture/expectation inputs and required dependency closure in declared durable locations. Scratch drafts and generated convenience views can remain in ignored `.azimuth/`; required inputs cannot survive only through ignored local paths. Tooling validates retention when completing work and CI validates it against the submitted revision. Do not copy every exploratory execution indiscriminately or omit adverse relied-on history.

CI assembles publication inputs deterministically from retained records and exact source/artifact identities. It transports unchanged reviewer records using the required reviewer identity/credentials, retains actual receipts and never manufactures approval. Publication does not authorize deployment. CI diagnostics remain diagnostics; Dima manually initiates correction work. No CI-generated work packages, assignments or Work Service protocol belongs to this workflow.


## Unchanged verification facet

When the requested implementation correction needs no verification transition, retain the explicit `facet-unchanged` decision described by `azimuth reference show facet-decisions`. Pin the actual accepted facet or verified absence. Do not create empty or artificial delta operations. The independent verification review still evaluates the decision and complete composed account.
