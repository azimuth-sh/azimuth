# Verification workflow

The account declares expectations; a Run records execution facts; independent reviews assess what those facts establish. Validation makes relationships and gaps visible without deciding a Requirement.

For the intended assurance control plane, harness boundaries, decision handling and production maintenance loop, see [intended-architecture.md](intended-architecture.md). That document describes direction rather than current executable contracts.

## Validate the exact account

Use `azimuth validate` for accepted state and `azimuth change validate <change>` for the prospective state. Project assessments accept a catalog and complete revision-pinned workset directly. The tool derives repository ownership and mounts; authors do not maintain projected workspace files or manually qualify manifests.

Validation separates structural validity, evidence completeness and acceptance readiness. A well-formed account can remain incomplete or unresolved. Pending reviews are obligations, not malformed declarations. No structural report proves execution, reviewer independence, deployed enforcement or acceptance.

## Select and execute

Execution requirements belong to Checks; a small policy routes generic execution families to explicitly configured capabilities. Local and CI environments can use the same policy with their own exact Verification Targets. Azimuth generates concrete selection rather than requiring a list of every Check ID. Missing declarations, incompatible inputs and unrouted Checks stay visible.

One bounded Run has one exact Verification Target and one semantic Plan. It may coordinate multiple adapters while retaining their individual bounded execution accounts and provenance. Source, artifact and deployed Verification Targets remain distinct. Build and deployment provenance can explain their relationship without treating Check Results as interchangeable.

A Check's Scenarios derive from authored Check-to-Scenario bindings unless an explicit subset is requested. Units default to one `whole` unit; finer planned work may be generated by a package or supplied explicitly. A complete whole unit does not imply complete endpoint coverage.

## Review incrementally

`azimuth assurance review-input` prepares a target-specific, fingerprinted packet containing authored definitions, dependencies, relevant exact-target Check Results, existing review assessments and gaps. It creates no reviewer identity, decision, rationale or approval. Reviewers retain responsibility for verification credibility and realization conclusions.

A Requirement that declares `Verification:` owes a Verification Review; one that declares `Realization:` owes a Realization Review. The Verification Review depends on the Requirement text, Scenarios, Checks and bindings, Challenge declarations and the Check execution units; the Realization Review depends on the Requirement text including its rigor declarations, the Scenarios, the realization declaration, the `realization.md`-derived mechanism fingerprints and the realization gaps; the Verification Review packet excludes realization sites and mechanisms entirely. Ordinary reruns and unrelated code changes do not require re-review; a changed blocking dependency does. Changes at realization sites are code drift — a boolean comparison of the review's `sites_fingerprint` with the current one — reported beside the Realization Review without staling it. Finalization stores the latest ratifying review of each kind in the model as a review head. Different Verification Targets and obsolete execution corrections remain distinct.

## Inspect state and resolve gaps

The ledger retains immutable Runs and the review heads carried by each main-model publication; the latest publication is the default model. It computes exact-Verification-Target Assurance State with the Verification Review assessment; deployment Requirement Status carries both review dimensions and code drift. Review assessment and Requirement conclusion are separate: an accepted, current Verification Review may still conclude unresolved. No Check success creates an approved review, and a supported state does not archive or accept a change automatically.

The working loop is author, validate, execute, review and resolve gaps. Validate again after integrating reviews and before explicit acceptance; acceptance-scope validation fails while any declared review lacks a current accepted record (`missing-requirement-assurance`, `missing-realization-review`) or a head names a Requirement that no longer declares its review (`unknown-review-head`).
