# Increment 2: behaviors

This is the list of behaviors for the second increment of the core. A person reads it before the build starts.

Each row is one observable fact about a command. The second cell is copied exactly from `docs/design.md`. A plain test fails when a quoted sentence is no longer in that file. A behavior with no sentence to quote is not built.

Status of this list: read and accepted by a person on 2026-11-17.

## The time limit of a launch

| Behavior | Quote from the design |
| --- | --- |
| A launch of an adapter has a time limit | **From the second increment a launch has a time limit, and the core stops the whole group of processes.** |
| The core starts each adapter and each proof in a process group of its own | starts each adapter and each proof in a process group of its own |
| At the limit the core sends SIGINT to the whole group, not to the adapter alone | asks the whole group to stop, with SIGINT, the signal of Ctrl+C |
| A process of the group that is still alive after the grace is killed with SIGKILL, together with the rest of the group | kills the whole group, with SIGKILL |
| The grace is 10 seconds and no setting changes it | The grace is one fixed number, 10 seconds to start with. |
| The suite of a launch that was stopped at the limit has the word `timed out` in `launch` | `launch` gets a fifth word, `timed out` |
| Every Check of that launch is owed with the reason `no result` | The Checks of the launch have the reason `no result`, and the run ends with status 1 |
| A run with a launch that timed out ends with status 1 | The Checks of the launch have the reason `no result`, and the run ends with status 1 |
| A test that had finished before the limit gets no result either, and nothing the adapter wrote is read | A launch that timed out gives no result for any of its Checks, also for tests that had finished, as for a launch that crashed. |
| The formats `adapter-request-1` and `adapter-report-1` keep their numbers | The request and the report do not change. |
| An adapter that receives SIGINT writes no report and exits | An adapter has one duty: when it is asked to stop, it writes no report and exits. |
| A Playwright launch that is stopped at its limit leaves no web server behind | after SIGINT the Playwright runner ran its teardown and stopped its web server |
| The limit of a suite is the key `time_limit_minutes` in the project file, a whole number | The key is `time_limit_minutes`, a whole number, and the default is 30. |
| A suite with no such key has a limit of 30 minutes | The key is `time_limit_minutes`, a whole number, and the default is 30. |
| A `time_limit_minutes` of zero, a negative one, or one that is not a whole number is a reading error | A value below 1, or one that is not a whole number, is a reading error, because a limit of zero stops every launch at once and can only be a mistake. |
| The key is optional and belongs to a suite, not to the project | **The time limit of a launch is one optional number per suite in the project file.** |
| The clock starts when the adapter starts and stops when it exits, so the build counts | The clock is wall time from the start of the adapter to its exit, so it includes the build. |
| A proof still counts as hung after 10 seconds, whatever the suite's limit is | A proof keeps its own 10 seconds. |
| The request holds no time limit | The adapter is not told the number, and the runner's own limits stay the runner's business. |
| A change of the number shows as class D | Raising it is an edit of the project file, so class D. |

## The runner's output during a run

| Behavior | Quote from the design |
| --- | --- |
| A launch where every test passed prints none of the runner's output | A launch where every test passed prints none of it. |
| A launch that crashed prints the runner's whole output on standard error after it ended | Trouble is a launch that crashed, timed out or failed its build, or one with a failed test. |
| A launch that timed out prints what the runner wrote up to the stop | Trouble is a launch that crashed, timed out or failed its build, or one with a failed test. |
| A launch whose build failed prints the output | Trouble is a launch that crashed, timed out or failed its build, or one with a failed test. |
| A launch with a failed test prints the output, also when other tests passed | Trouble is a launch that crashed, timed out or failed its build, or one with a failed test. |
| The output of a launch is printed in one piece, after the launch ended, and not mixed with another launch | Then the output of that launch is printed whole on standard error, after the launch ended. |
| The core prints one line when a launch starts and one when it ends | The core prints one line when a launch starts and one when it ends, so a long launch does not look like a hang. |
| While a launch runs, its output is in a file under `.azimuth/` | While a launch runs, the core writes the held output to a file under `.azimuth/`, and removes the file after a launch with no trouble. |
| After a launch with no trouble that file is gone | While a launch runs, the core writes the held output to a file under `.azimuth/`, and removes the file after a launch with no trouble. |
| With `--json` standard output holds only the one document, and the held output goes to standard error under the same rule | With `--json` the rule is the same: standard output holds the one document, and the held output goes to standard error. |

## Rules of the contract for every adapter

| Behavior | Quote from the design |
| --- | --- |
| An adapter starts its runner with retries turned off, also when the runner's configuration turns them on | The adapter owns the runner's command line, so it turns retries off whatever the runner's configuration says. |
| A test that fails on its first attempt is reported as `failed` | **An adapter reports the first attempt of each test and turns the runner's own retries off.** |
| An adapter does not run tests against a process that was started before the launch | An adapter does not let the runner use a process that was started before it. |

## The Playwright adapter

| Behavior | Quote from the design |
| --- | --- |
| The second adapter runs Playwright tests | **The second adapter is the one for Playwright.** |
| Its package is `@azimuth-sh/playwright` on npm | **The Playwright adapter is the npm package `@azimuth-sh/playwright`, and the project file says `npx --no @azimuth-sh/playwright`.** |
| Started from a copy outside the application's installation, the adapter ends with a failure and says that the package is not installed in this application | Otherwise it ends with a failure and says that the package is not installed in this application, and the launch is `crashed`. |
| It runs from a `node_modules` folder of the folder named in the request or of a folder above it | It runs only from a `node_modules` folder of the folder named in the request, or of a folder above it. |
| It is installed as a development dependency of the application's package | The package is a development dependency of the application whose tests it runs, and it has one command. |
| The package has one command, so `npx` starts it by the package's name | The package is a development dependency of the application whose tests it runs, and it has one command. |
| With the adapter not installed, the suite's command line ends with a failure and downloads nothing | `--no` keeps `npx` from downloading a package, so a missing adapter ends with a message of `npx`: it may ask the registry about the name, and it downloads and runs nothing. |
| Its code is in `adapters/playwright/` | Its code is in `adapters/playwright/` of the Azimuth repository. |
| Azimuth's own tests install it from a packed file and reach no registry | Azimuth's own tests pack it into a file and install it from that file, so they need no registry. |
| Its pin is the package's `package.json` with the lock file, so an upgrade makes the Checks owed | The pin is a file of the repository, so it is already an input: an adapter upgrade makes the Checks owed. |
| The core starts it in the suite's folder, where the package's own installation is found | An adapter starts in its suite's folder so that each stack finds its own pin. |
| The suite's folder holds the Playwright config, and the adapter passes the runner no path to it | A Playwright config goes into the folder of its tests. The adapter starts there, and the runner finds its configuration by itself. |
| Two suites of one package, each with its own config, need nothing more than two entries in the project file | The contract of an adapter needs nothing new for a package that holds two suites. |
| Arguments on the adapter's command line in the project file reach the adapter as written | The core adds none and passes the line on as written. |
| A test carries a Check id in a tag of the form `@<marker_key>:<id>` | **In Playwright the marker is a tag, `@<marker_key>:<id>`.** |
| The tag may stand on a test or on a `describe` group, and a test may carry several | It stands on a test or on a `describe` group, and a test may carry several. |
| An annotation with a Check id is no marker | The other candidate was an annotation. |
| The adapter finds marked tests by the suite's `marker_key` from the request | The adapter asks the runner by key, and the core sends it the suite's `marker_key` in the request. |
| It runs only the tests of the Checks asked for, through the runner's own filter | The runner already filters by its own tag, and the adapter passes it the ids of the owed Checks. |
| Its report lists every marked test of the suite, also the ones not asked for | A report always lists every marked test of the suite, also the ones not asked for. |
| Each test has the outcome `passed`, `failed`, `skipped` or `not_run`, and a duration | Per test it says `passed`, `failed`, `skipped` or `not_run`, with a duration, and whether the Check passed is the core's rule. |
| A test that the config runs in several browser projects is one entry | **A test that the runner runs several times under different settings is one entry as well.** |
| That entry is `failed` when the test failed in any project, and `passed` only when it passed in all | The entry failed if the test failed in any of them, it passed only if it passed in all of them, and its duration is the sum. |
| The duration of that entry is the sum over the projects | The entry failed if the test failed in any of them, it passed only if it passed in all of them, and its duration is the sum. |
| The adapter reads the resolved config before it starts any test | It reads the resolved config before it runs anything. |
| With `reuseExistingServer` true in the resolved config it runs nothing, names the setting, and the Checks get no result | If `reuseExistingServer` is true, or there is no `webServer` entry, it runs nothing and says why, and the Checks get no result. |
| With no `webServer` entry in the resolved config it runs nothing, says so, and the Checks get no result | If `reuseExistingServer` is true, or there is no `webServer` entry, it runs nothing and says why, and the Checks get no result. |
| A refusal writes the reason to standard error, ends with a status other than 0, and writes no report | **A refusal is a launch with no report.** The adapter writes the reason to standard error and ends with a status other than 0. |
| The suite of a refused launch reads `crashed`, and its Checks are owed with `no result` | The launch reads `crashed`, and its Checks are owed with the reason `no result`. |
| When the runner cannot list the suite's tests, the report holds `"build": "failed"` and no tests | The Playwright adapter reports `"build": "failed"` and no tests when the runner cannot list the suite, for example after a syntax error in a test file. |
| Every Check of such a suite is owed | The effect is the one of a .NET build that fails: every Check of the suite is owed. |
| It reports its name and version, and the version is stored with each result | The adapter reports its version, which is stored with each result. |
| A Playwright adapter that is not installed gives a launch that reads `crashed`, as a missing .NET adapter does | An adapter that is started through a host program, such as `dotnet azimuth-xunit`, cannot be told from a crashed one when it is missing |
| It ends with status 0 when it wrote a report, also when tests failed | 0 when a report was written, also when tests failed. Anything else means the launch crashed |
| It writes the report to standard output, and the runner's output goes to standard error | one JSON document on its standard output. The runner's own output goes to standard error |

## `azimuth init` and the table of known runners

| Behavior | Quote from the design |
| --- | --- |
| The CLI's table of known runners has an entry for Playwright: how to recognize it, the marker form, the adapter's command and its install line | **The CLI carries a small table of the runners it knows.** |
| The entry's command line is `npx --no @azimuth-sh/playwright` | **The Playwright adapter is the npm package `@azimuth-sh/playwright`, and the project file says `npx --no @azimuth-sh/playwright`.** |
| The install line that init and run print is `npm install --save-dev --save-exact @azimuth-sh/playwright@<version>`, with the CLI's version filled in | For Playwright the install line is `npm install --save-dev --save-exact @azimuth-sh/playwright@<version>`. |
| The printed line names the version of the CLI that prints it | **The line that installs an adapter names the version of the CLI that prints it.** |
| `azimuth lint` finds Playwright markers in a suite's files by the marker form of that entry | the core scans the suite's files for the marker's text form |
| In a repository with a Playwright stack whose adapter is not installed, init prints the install line and says that this stack's suites are not in the project file | For another stack it prints the install line and says that this stack's suites are not in the project file. |
| Init asks the adapter with the verb `discover` from the root of the repository | **For `discover` the adapter starts at the root of the repository.** |
| From the root an adapter that is installed only inside an application's folder is not found | An adapter that is installed only inside an application's folder is not found from there. |
| Init also starts the adapter with `discover` in each folder whose `package.json` lists `@azimuth-sh/playwright` among its dependencies | **Init also asks an adapter in each folder whose package manifest lists it.** |
| That request names the manifest's folder, and the suites init writes are the test projects reported under it | Init starts the adapter in that folder and names that folder in the request, and the adapter reports the test projects under it. |
| For `discover` the Playwright adapter reports each folder that holds a Playwright config | For Playwright a test project is a folder that holds a Playwright config. |
| A `package.json` under `node_modules`, or in any folder that git ignores, is not read | Init reads only manifests that git does not ignore, so `node_modules` stays out. |
| A manifest that lists the adapter while the adapter cannot be started gives the install line and no suite | A manifest that lists the adapter while the adapter cannot be started is a stack whose adapter is not installed. |
| Init sees a Playwright stack where a `package.json` lists `@playwright/test` | A Playwright stack is recognized by a `package.json` that lists `@playwright/test`. |
| Init writes the repository's name from the last part of the remote's address, without `.git` | The name is the last part of the address, without `.git`. |
| In a git worktree whose folder has another name, init writes the name from the remote and not the folder's | **`azimuth init` takes the target from the remote's default branch and the repository's name from the remote's address.** |
| With no remote init writes the name of the root folder | With no remote the name is the one of the root folder. |
| `azimuth run` names the missing command of a Playwright suite and prints the install line | `azimuth run` says which command is missing and how to install it, and `azimuth init` prints the same line for each stack it found. |

## The id in a marker

| Behavior | Quote from the design |
| --- | --- |
| With a marker form that ends with `<id>`, the id ends at the first character that is not a letter, a digit or a hyphen | **When the form ends with `<id>`, the id ends at the first character that is not a letter, a digit or a hyphen.** |
| With a text after `<id>` in the form, the id ends where that text starts | With a text after `<id>` in the form, the id ends where that text starts. |

## The release

| Behavior | Quote from the design |
| --- | --- |
| The release workflow packs the Playwright adapter with the version of the release and stages that packed file at npm | the workflow builds and packs everything, makes the draft release and stages the npm package |
| The workflow runs `npm stage publish` and never `npm publish` | The workflow runs `npm stage publish` and never `npm publish` |
| The package names its license, the project's site and the source repository, and carries a short readme | **A package says where it comes from.** A published version cannot be changed, so each adapter package names its license, the project's site and the source repository, and carries a short readme. |
| The workflow holds no npm token | The workflow stores no registry key: it trades its identity for a short-lived one, which the registry calls trusted publishing |
| The job that stages at npm and the job that makes the draft release do not name the environment `release` | The workflow does every first phase before it asks for the approval, so a failure there burns no version. |
| The release is first made as a draft with every file attached | a draft with every file attached |
| The job that pushes to NuGet starts only after the draft is made and the npm package is staged | The approval is asked for only when step 1 is green |
| The draft is published only after the push to NuGet succeeded | the workflow pushes to NuGet, and then it publishes the draft |
| The push to NuGet skips a version that is already there | A push that is run again skips a version that is already there |
| The job uses no action from a party that the release path does not trust already | an action comes only from a party the release path already trusts |

## `azimuth change diff`

| Behavior | Quote from the design |
| --- | --- |
| The command that compares a branch with its target is `azimuth change diff` | **The command is `change diff` because it compares, and it takes no id.** |
| `azimuth change show` is an unknown command | The earlier name `change show` is not kept as a second name. |
| In the plain form each added, changed or removed id stands on a line of its own under its kind | In the plain form each id stands on a line of its own under its kind, because a person reads this list at the stop before a merge. |
| A changed file with a marker that the target does not have gets no line "tests in this file were not compared" | **A file that the target does not have is not named there.** |
| Such a file is absent from `not_compared` in the structured form | It is absent from the plain form and from `not_compared` of the structured form. |
| A changed file with a marker that the target has still gets the line | For every changed file that holds a marker, `azimuth change diff` adds the line "tests in this file were not compared". |
| For a change that touches no model file and no test the command prints one line | the change touches no model file and no test, and then it prints one line |
| The shipped skill names the command `azimuth change diff` at both stops | The person reads `azimuth change diff` before any code exists |

## Repairs that change no behavior

These come from the first real use of increment 1. They change no output and no format, so they quote nothing.

- `azimuth change diff` reads the files of the base tree through one git process. Today it starts one process per file of every suite, and its time grows with the number of test files and not with the size of the change.
