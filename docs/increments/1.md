# Increment 1: behaviors

This is the list of behaviors for the first increment of the core. A person reads it before the build starts.

Each row is one observable fact about a command. The second cell is copied exactly from `docs/design.md`. A plain test fails when a quoted sentence is no longer in that file. A behavior with no sentence to quote is not built.

Status of this list: read and accepted by a person on 2026-11-16.

## The model files

| Behavior | Quote from the design |
| --- | --- |
| The model is read from module folders at any depth under `azimuth/model/` | **A module is a folder in the model tree, at any depth.** |
| A module folder may lack any of its files, and that is not a finding | All of them are optional. |
| A Requirement or a Scenario is recognized by a heading that holds its structure word and an id | A heading holds a structure word and an id |
| A heading is recognized at any heading level | Lint reads the structure word, not the heading level |
| A line that starts with `Context`, `Realization`, `Verification` or `Reuse` and a colon is read as a declaration, wherever it stands under its heading | A line that starts with a declaration word and a colon is a declaration, wherever it stands under its heading |
| A blank line between a heading and a declaration changes nothing | Position cannot carry meaning in Markdown, because blank lines move when a file is formatted |
| A line that starts with any other word and a colon is prose | a line that starts with any word other than a declaration word, and a colon, is prose |
| A key or a table in the project file that the CLI does not know is a reading error | a key or a table that the CLI does not know is a reading error |
| The text under a heading is accepted in any language and is never judged by lint | The text under the heading is free prose, in any language |
| No Scenario is refused for lacking Given, When, Then | No required Given, When, Then |
| A review is declared as `Verification: reviewed` or `Realization: reviewed` | A declaration is written `Verification: reviewed` or `Realization: reviewed`. |
| A Check is read from `verification.md` under its Scenario, as an id, a claim and an optional `Reuse:` | The declaration is the id, the claim and `Reuse:` when present. |
| A `Reuse:` field without a reason is a reading error | The `Reuse:` field on a Check limits that, and it always carries a reason. |
| `Reuse:` is written on one line as a value, a comma and a reason | `Reuse: <value>, <reason>` on one line |
| The reason is the text after the first comma, without the spaces and tabs around it, and may be in any language | the text after the first comma, to the end of the line, without the spaces and tabs around it. Free prose in any language |
| `never` is the one value this version knows | `never` in the first increment. `for N days` arrives later |
| A `Reuse:` line with no comma, with nothing but spaces and tabs after the comma, or with an unknown value is a reading error | no comma, nothing but spaces and tabs after the comma, or a value the CLI does not know |
| A Check declared without `Reuse:` is reused by equal fingerprint | A result is reused by default. |
| Two Checks with one id anywhere in the project are a reading error | **A Check id is unique in the whole project too. A Scenario id is unique within its Requirement.** |
| Two Scenarios with one id in one Requirement are a reading error | nothing ever names a Scenario without its Requirement |
| Two Scenarios with one id in different Requirements are valid | The identity of a Scenario is the pair of Requirement id and Scenario id. |
| A Scenario heading with no Requirement heading above it is a reading error, also in `verification.md` | In `verification.md` a Scenario heading therefore stands under its Requirement heading. A Scenario heading with no Requirement heading above it is a reading error. |
| Two Requirements with one id in different modules are a reading error | **A Requirement id is unique in the whole project and does not contain the module path.** |
| An id with a capital letter, a space or a letter outside the Latin alphabet is a reading error | **An id is written by hand in lowercase Latin letters, digits and hyphens.** |
| A heading with a structure word and no id is a reading error | an id used twice where it must be unique, a wrong character in an id, `Reuse:` with no reason, a structure word with no id, an unknown key in the project file |
| On a reading error `azimuth run`, `azimuth check run` and the reading commands print the message, do nothing else and end with failure | print the same message, do nothing else, end with failure |
| A reading error has the same words in every command | Every command reads the model through the same reader, so a reading error has the same words everywhere. |
| With a finding that is not a reading error, `azimuth run` and the reading commands work | work. The affected Check is shown with the state it has |
| Moving a module folder changes no Requirement id and no fingerprint of a claim | Moving a module is a rename of a folder, and no Requirement gets a new identity. |

## `azimuth init`

| Behavior | Quote from the design |
| --- | --- |
| The project file is `azimuth/project.toml`, written in TOML | **The project file is TOML.** |
| The project file has the keys `cli`, `repository`, `area`, `suite` and `facility` | Its content in the first increment of the core: |
| It writes the project file with this repository and one area that covers all of it | writes the project file with this repository and one area that covers all of it, lists the test projects that the adapter finds as suites, and creates `.azimuth/` with its own ignore file. The model stays empty |
| It lists as suites the test projects that the adapter finds | **A suite is declared.** It is one test project by default. |
| For `discover` it starts the adapter at the root of the repository | **For `discover` the adapter starts at the root of the repository.** |
| It writes the marker form of each suite whose runner it knows | `azimuth init` writes it for runners it knows. |
| It creates `.azimuth/` holding a `.gitignore` that contains `*` | The folder holds a `.gitignore` that contains `*`. |
| It creates no Requirement and no module | After `azimuth init` nothing is visible. |
| Run a second time, it changes nothing | It never changes a file that exists. |
| It writes no skill file | It installs no process: the skills of the default process come from a separate command, `azimuth skills install`, for a named agent harness. |
| It recognizes a stack whose adapter is absent by the table of runners in the CLI | **The CLI carries a small table of the runners it knows.** That is how `azimuth init` sees a stack whose adapter is absent. |

| For a stack whose adapter is not installed, it prints which command is missing and how to install it | `azimuth run` says which command is missing and how to install it, and `azimuth init` prints the same line for each stack it found. |
| It prints the line for the CI job with the lane flag | `azimuth init` prints the CI line with the flag |
| It writes no facility definition | `azimuth init` writes none, and a person adds a facility when a suite needs one. |
| The target it writes is the remote's default branch as the clone already knows it | The target branch it writes is the remote's default branch as the clone already knows it. |
| With no remote, the target it writes is the current branch | With no remote it is the current branch. |
| It writes the target branch into the project file from what git holds locally | `azimuth init` writes it from what git already holds locally |
| It needs no account and no network | **Starting on the core rung takes four steps, and none of them needs an account or a network.** |

## The pinned CLI version

| Behavior | Quote from the design |
| --- | --- |
| The project file holds one exact CLI version, and a range is refused | The pin is exact, not a range, while versions start with 0. |
| With another version, lint and the reading commands work and print a warning | the reading commands and lint work and print a warning. `azimuth run` refuses, and prints the command that installs the pinned version |
| With another version, `azimuth run` runs nothing and prints the command that installs the pinned version | `azimuth run` refuses, and prints the command that installs the pinned version |
| Under another version, lint and the reading commands print one warning line on standard error that names the pinned version | The warning under another version is one line on standard error that names the pinned version. |
| Changing only the pinned version in the project file moves the files part and no other part | the pin is a line in the project file, which is a tracked file, so raising it moves the files part and no other part, and every Check is owed once |

## `azimuth lint`

| Behavior | Quote from the design |
| --- | --- |
| It reports reading errors and findings, and ends with failure on either | **A reading error stops every command. A finding fails only lint and the commit lane.** |
| With no finding it ends with status 0, with a finding with 1, and on a reading error with 2 | **A command ends with one of three statuses.** |
| Its document is `lint-1` with these fields | `findings`, each with `kind`, `file`, `line` and `message` |
| It runs no test and proves no facility | It runs no tests and needs no facilities. |
| It works with no adapter installed and without building anything | Lint must not need a build. |
| It finds markers by scanning each suite's files for that suite's marker form | The suite's declaration names its marker form, for xUnit the text `[Trait("Check", "<id>")]`. |
| A project may declare a marker key other than `Check` | A project may declare another key when `Check` collides with a tag it already uses. |
| A suite's `marker_key` is sent to the adapter in the request, and without the key the request says `Check` | **The other key is the suite's optional `marker_key`, which defaults to `Check`.** |
| `azimuth init` writes no `marker_key` | `azimuth init` writes no `marker_key`. |
| A `marker_key` that the marker form does not use leaves the Checks of the suite with no result at the launch | The launch finds markers in source that match no listed test, and those Checks get no result. |
| It reports a line whose first word is one or two letters away from a declaration word | a line whose first word is one or two letters away from a declaration word is a lint finding |
| It reports a marker that names an unknown Check | Lint works from source alone. It finds a marker that names an unknown Check and a Check with no marker. |
| It reports a Check that no marker names | A Check with no marked test |
| It reports one Check id marked in two suites | The same Check id marked in two suites is a lint finding. |
| It reports a heading in `verification.md` whose id exists nowhere in `specification.md` | An id is written in up to three files and in the markers, so a rename touches all of them, and lint names every place that disagrees. |
| Text above the first Requirement in `specification.md` is prose, also under a heading that says `Term`, and gives no finding | Until approvals exist, a definition is plain prose above the first Requirement in `specification.md`. Lint reads it as prose and knows no `Term`. |
| It reads nothing inside `realization.md` and reports nothing about it | **Until increment 4 nothing inside `realization.md` is read.** It is prose. |
| It resolves no structure unit and reads no profile | The first increment of the core has no structure units. |
| It does not report a Scenario that has no Check | A Scenario with no Check is not a lint finding. It is a gap, and status names it. |
| It does not report an owed Check or a missing result | It does not report missing results. |
| It reports a tracked file under `.azimuth/` | Lint refuses a tracked file under `.azimuth/`. |
| Every finding says what is wrong and what to do | A lint finding itself says what is wrong and what to do. |
| It ends with a failure status when there is a finding | It is the first step of the commit lane, and a finding blocks that lane. |

## The fingerprint

| Behavior | Quote from the design |
| --- | --- |
| With no input provider, every file of the repository is an input of every Check | Without an input provider, every file of the repository is an input of every Check. |
| Declaring a smaller area changes no Check's inputs | **An area is a hand-written list, so an area never narrows an input by itself.** |
| An edit to a tracked file changes the fingerprint before it is staged or committed | **The tree on a developer's machine is what git would commit if everything were staged now.** |
| A new file that git does not ignore is an input before any `git add` | A new file changes the build before it is committed, so tracked files alone are not enough. |
| Staging a change does not move the fingerprint | Staged or unstaged makes no difference. |
| An edit to a file that git ignores moves no fingerprint | One limit. An ignored file can change a local result, and Azimuth cannot see it. |
| A clean checkout of a commit gives the digests of claim and files that the working tree had when it held exactly that content | After a commit of exactly that state, CI computes equal digests for the claim and the files, so a local result and a reference result describe the same content. They differ only in the environment part. |
| A file is hashed in the form git stores, so a checkout with other line endings gives an equal fingerprint | **Code and other input files are hashed as exact bytes, as git stores them.** |
| A claim that differs only in Unicode form, in line endings, or in spaces and tabs at line ends has an equal digest | The Unicode form is NFC. Every line ending becomes LF. Spaces and tabs at line ends are removed. Nothing else is folded. |
| A claim that is re-wrapped or restyled has a different digest | Re-wrapped paragraphs and Markdown styling would need a parser inside the digest, and a parser upgrade would then make every review stale. |
| Without a provider the fingerprint has the parts claim, files, environment and method | **Without a provider the fingerprint has four parts.** |
| For a tree that is exactly a commit, the store keeps the id of that commit's tree and no list | **A stored tree is a commit plus what differs from it.** |
| For a commit with local edits, the store keeps that tree id plus one entry per edited, new or deleted path | the id of that commit's tree, plus one entry per path that is edited, new or deleted |
| Kept or owed is decided without reading a list of files | Kept or owed is decided by the digest of the files part alone, and the decision never reads the list. |
| When git no longer has the stored tree, the reason says "files changed" and names no file, and no state changes | If git no longer has that tree, the explanation shrinks: status says "files changed" and names no file. |
| On a developer's machine the environment part is one fixed value | one fixed value on a developer's machine. No fact is measured |
| A `text-1` digest is the SHA-256 of the normalized text, written as lowercase hex | The hash is SHA-256, written as lowercase hex |
| The method part holds the scheme names and the object format of the repository | the scheme names and the object format of the repository |
| The digest of a file is the object id git gives its content | **The digest of a file is git's own object id.** Azimuth does not hash file content with an algorithm of its own. |
| For an edited or a new file the id is that of the content in the working tree, and nothing is written into git's object store | For an edited or a new file, git computes the id of the content in the working tree without storing it. |
| A change of only a file's mode changes the files part | The list of a tree holds the path, the mode and the id of each file, as git's own tree does. |
| A digest is written as its scheme name, a colon and the value | A digest is written with its scheme, as in `text-1:9f3a`, and two digests of different schemes are never equal. |
| The digest of model text names `text-1`, of a file `file-1`, and a fingerprint `parts-1` | **A scheme is a named rule for computing one kind of digest.** Its name is a word and a number, and the number goes up whenever the same content could give a different digest. |
| A stored result whose digests name another scheme number is not compared, and its Check is owed | A result under another number is not comparable, so its Check is owed. |
| The owed reason names the scheme that changed | The owed reason names the scheme that changed, for example "method changed: `parts-1` became `parts-2`". |
| No setting and no flag chooses a scheme | The scheme is not a setting: it comes with the CLI version, which the project file pins, so every machine of a project uses the same numbers. |
| Every stored digest names its scheme | **Every digest names the scheme that produced it.** |
| A result stores the digest of each part of its fingerprint | **The digest of each part is stored with the result.** |
| The adapter's reported version is stored with the result and moves no fingerprint | **The adapter's version is recorded with each result and is not part of the fingerprint.** |
| Restoring earlier content makes the earlier pass valid again | **Validity follows content, not commits.** Going back to earlier content brings the earlier pass back. |
| No record names a commit as its identity | **Nothing in Azimuth points at a commit as identity.** |

## `azimuth run`

| Behavior | Quote from the design |
| --- | --- |
| It starts only the adapter command named in the project file and downloads nothing | The project file names the command of each suite's adapter. The core starts that command and reads its report. |
| With the adapter missing, it runs nothing and says which command is missing and how to install it | A missing adapter is a named state. |
| It computes each Check's fingerprint before it starts anything | 1. The core computes each Check's input list and fingerprint from the tree. |
| It proves each declared facility of a suite before the launch | **A suite declares the facilities it needs,** for example Docker or `python3`. Each is proven before the launch. |
| It proves a facility by running the proof command that the project file defines for it | **A facility is a name and a proof command, defined once in the project file.** |
| A proof that fails, hangs past its time limit or has no definition means "cannot run here" | A proof that fails, hangs or is missing means "cannot run here". |
| No flag and no setting marks a facility as present | A proof is a command, and never a setting. Nothing in the tree and nothing on the command line can say "present". |
| With a facility missing, the suite's Checks are owed with the reason "cannot run here" and none is failed | **A missing facility is never a fail.** The Check is owed with the reason "cannot run here". |
| It builds and starts the test process through the adapter | 3. It starts the build and the test process through the adapter. |
| It asks the runner only for the tests of owed Checks | A launch asks the runner only for the tests of owed Checks |
| It never starts a test that has no marker | **A test without a marker does not exist for Azimuth.** |
| A Check with a valid result is not run | **A result is valid when it is a verified pass with a fingerprint equal to the current one.** |
| A second run on an unchanged tree runs nothing | A second run on an unchanged tree is kept, and going back to earlier content brings the pass back |
| A Check that failed on the current fingerprint is not run again on a developer's machine | Skipped locally, run again in CI |
| A Check with `Reuse: never` is not run on a developer's machine and is shown as "runs in CI" | Skipped, shown as "runs in CI" |
| A marker on a class enrolls every test of the class | It is valid on a test method, or on a test class, where it means all tests of the class. |
| It gives no result when the tests run differ from the tests listed | 4. It reads the report and verifies that the tests run equal the tests listed. |
| A marker in source that matches no listed test is a finding, and that Check gets no result | The launch compares the two lists: a marker in source that matches no listed test, or a listed test whose Check id appears nowhere in source, is a finding, and that Check gets no result. |
| A listed test whose Check id appears nowhere in source is a finding, and that Check gets no result | It does not pass silently, because the launch reports a test whose Check id source does not show. |
| When the suite does not build, no Check of the suite gets a result | the launch fails for every Check of that suite, because the suite is built as a whole |
| A Check fails when any of its marked tests failed | Any test failed |
| A Check gets no result when a marked test was skipped or not run and none failed | Otherwise, any test inconclusive, skipped or not run |
| A Check passes only when every marked test ran and passed | A Check states one claim about a Scenario, and it passes only when every enrolled test ran and passed. |
| It hashes the inputs again after the tests ran | 5. It hashes the inputs again. |
| When an input changed during the launch, no result is written | **If any input changed while the launch ran, the launch gives no results.** |
| When the launch crashes, no result is written | **A launch that crashes gives no results.** |
| Each result stores the names of the tests it enrolled | Every result stores the names of the tests it enrolled, so "fewer than before" is a comparison of two lists. |
| Each result is written with its fingerprint and part digests | 6. It applies the Check rule and writes each result with its fingerprint and part digests. |
| No command accepts a result from a file or a test report | **A result produced this way is called verified.** Nothing written by hand or imported from a test report counts. |
| A fail on one fingerprint leaves a pass on another fingerprint in place | **A fail never erases a pass on other content.** |
| A later result on one fingerprint is added beside the earlier one | **One fingerprint may hold several results,** for example a pass and later fails. |
| The duration of each launch is stored | **Cost is measured.** Durations are stored and feed ranking and time limits. |
| It writes results to the outbox of its own worktree and then runs the local step of sync | Every command that creates a record then tries to sync at once. |
| Where it may not write the store, the results stay in the outbox and it says how many records wait | Where the session is not allowed to write the store, the record stays in the outbox. The CLI reports how many records wait. |
| It writes nothing into a tracked file | **Nothing is committed.** |
| The local lane runs no lint and reports no finding | the local lane. No lint, apart from stopping on a reading error |
| A lane that ends with failure ends with status 1, and one that ends with success with 0 | a failed Check, an owed Check in the commit lane, a lint finding |
| On a reading error, a wrong argument or a CLI version other than the pinned one it ends with status 2 | a reading error, a wrong argument, `azimuth run` under a CLI version other than the pinned one, a missing common ancestor |
| Its document is `run-1` with these fields | `lane`, `outcome`, `suites` with `name` and `launch`, `checks` with `id`, `state`, `reason`, `detail`, `failing_tests` and `duration_ms`, and `findings` in the commit lane |
| `suites` lists only the suites whose adapter the core started or tried to start | only the suites whose adapter the core started or tried to start |
| A suite with a missing facility or with nothing to run is not in `suites` | A suite with a missing facility or with nothing to run is not listed, and its Checks say why. |
| When an input changed during a launch, `launch` is `ok` and the Checks have the reason `no result` | When an input changed during the launch, `launch` is `ok` and the Checks say `no result` |
| A Check's `duration_ms` is the sum of the durations of its tests in this run, and is absent when the Check did not run | the sum of the durations of its tests in this run. Absent when the Check did not run |
| A Check that ran in this command is `passed` or `failed`, and one that did not is `kept` or `owed` | Only a Check that ran in this very command is `passed` or `failed`. |
| On a reading error the document is `error-1` with these fields | `errors`, each with `kind`, `file`, `line` and `message` |
| A Check whose launch gave no result is `owed` with the reason `no result`, and `detail` names the cause | in `run-1` the state is `owed`, the reason is `no result`, and `detail` names the cause |
| After a launch with no result, `azimuth status` shows the Check with the reason it had before the run | A launch with no result stores nothing, so a later `azimuth status` shows such a Check with the reason it had before the run. |
| A Check with `Reuse: never` is `owed` with the reason `runs in CI` on a developer's machine | the state is `owed` and the reason is `runs in CI` |
| `outcome` is `success` or `failure`, and `launch` is `ok`, `build failed`, `crashed` or `not started` | `outcome` is `success` or `failure`. `launch` is `ok`, `build failed`, `crashed` or `not started` |
| `findings` is absent in the local lane | present only in the commit lane |
| A proof and an adapter are started with no shell, from a command line split on spaces | **The core starts a proof or an adapter directly, with no shell.** The command line from the project file is split on spaces. |
| An adapter starts in its suite's folder | An adapter starts in its suite's folder, and a proof starts at the root of the repository. |
| A proof starts at the root of the repository | An adapter starts in its suite's folder, and a proof starts at the root of the repository. |
| A proof and an adapter get the environment of the CLI | The environment is passed on unchanged. |
| The core adds no argument to an adapter's command line and passes on the arguments written in the project file | The core adds none and passes the line on as written. |
| A proof that runs longer than 10 seconds counts as hung, and its suite cannot run here | A proof that runs longer than 10 seconds counts as hung, and the number is fixed in the first increment. |
| An unknown command, flag or lane, and an unknown id of a Check or a Requirement, end with status 2 | A wrong argument is anything the CLI does not know: a command, a flag, a lane, or the id of a Check or a Requirement. |
| With no flag it runs the local lane | local, the default |
| It reads no environment variable to choose a lane | Nothing is detected from the environment. |
| It goes on after a failed test and reports every Check with its state | **A run never stops at the first failure.** It runs everything the lane planned and then reports every Check with its state. |
| A suite that does not build stops only its own Checks | A suite that does not build, a launch that crashes or a missing facility stops only its own suite. |
| It ends with failure when any Check is failed on the current content | any Check is failed on the current content, whether it ran now or is a known fail |
| A second run on unchanged content after a failure runs nothing and ends with failure again | **The status follows the state of the tree, never what happened to run this time.** |
| It ends with status 1 when a suite did not build | A Check that is still owed after the run because its launch gave no result ends the run with status 1. |
| It ends with status 1 when a launch crashed | A Check that is still owed after the run because its launch gave no result ends the run with status 1. |
| It ends with status 1 when the adapter did not start, and the Checks of that suite are owed | the suite did not build, the launch crashed, the adapter did not start, an input changed during the launch, a marker in source matched no listed test, a marked test was skipped or not run |
| It ends with status 1 when an input changed during the launch | A Check that is still owed after the run because its launch gave no result ends the run with status 1. |
| It ends with status 1 when a marker in source matched no listed test | A Check that is still owed after the run because its launch gave no result ends the run with status 1. |
| It ends with status 1 when a marked test was skipped or not run | A Check that is still owed after the run because its launch gave no result ends the run with status 1. |

## The local store and `azimuth sync`

| Behavior | Quote from the design |
| --- | --- |
| The store is the folder `azimuth/` in the clone's shared git directory | The CLI asks git where the clone's shared directory is and keeps its files in `azimuth/` inside it. |
| Two worktrees of one clone see the same results | Every worktree of the clone sees the same store. |
| The store is plain files with no index and no database | Plain files in a folder of the working tree that ignores itself. No index and no database |
| A record still in the outbox is read like a record in the store | **Reading uses both places.** A sandboxed session can read the store even where it cannot write it. |
| With no server address, `azimuth sync` moves records from the outbox into the store and does nothing else | the local step, and nothing else |
| A record in a format this version cannot read counts as absent, and its Check is owed | it counts as absent, so its Check is owed. `azimuth status` says in one line how many such records it skipped |
| `azimuth run` writes each result as a record whose `format` is `result-1` | **A stored result is a record of the format `result-1`.** |
| A record's `body.outcome` is `passed` or `failed`, and a crash or a skipped test writes no record | `passed` or `failed`. Nothing else is stored, because a crash or a skipped test gives no result |
| A record's body holds `fingerprint` and, under `parts`, the digests of `claim`, `files`, `environment` and `method` | the digests of `claim`, `files`, `environment` and `method` |
| A record of a run on exactly a commit holds that commit's tree id as `body.tree.base` and no `edits` | `base`, the tree id of the commit, and `edits`, one line per path that is edited, new or deleted. |
