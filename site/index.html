Azimuth

Agents write the code. People stay responsible for it.

Azimuth lets people direct and review software work at the level of intent, and it shows with evidence how far the code matches that intent.

You write Requirements and their Scenarios as plain text. Tests are bound to them as Checks. After a change, Azimuth works out which Checks must run again, runs them, and tells you which Requirements are proven.

“Proven” is a status: every Scenario has a Check that passed on exactly this code. It does not mean the code is correct. Intent nobody wrote is unprotected, and a Check can be weak.

What it looks like

A Requirement, in azimuth/model/lending/specification.md

### Requirement: loan-limit-holds
A borrower holds at most five loans at a time.

#### Scenario: sixth-loan-is-refused
A borrower who holds five loans asks for a sixth book.
The desk refuses the loan and the borrower keeps five.

The Check that stands for the Scenario, in verification.md beside it

### Requirement: loan-limit-holds
#### Scenario: sixth-loan-is-refused
- Check: sixth-loan-is-refused
  The desk refuses a sixth loan to a borrower who holds five.

The test that is the Check, marked in the code

[Fact]
[Trait("Check", "sixth-loan-is-refused")]
public void Refuses_a_sixth_loan() { ... }

Before the test has run on this code

$ azimuth status
Requirement loan-limit-holds (lending): incomplete
  Scenario sixth-loan-is-refused
    sixth-loan-is-refused  owed: never run
  verification: not reviewed
  realization: not reviewed
  approval: not recorded

After azimuth run

$ azimuth status
1 Requirement, proven on this machine

Change the code, and the Check is owed again until it has passed on the new code.

Status

Azimuth is an early alpha. Formats and commands still change between versions, so a repository pins one exact version.

What exists

  • The command line tool, for macOS on arm64 and Linux on x86-64.
  • The adapter for xUnit, the package Azimuth.Xunit.
  • A default process for an agent, installed as a skill for Claude Code or Codex.

What does not exist yet

  • Adapters for other test runners.
  • Narrow change tracking. Today any change to a file of the repository makes every Check owed.
  • Recorded reviews and approvals.
  • The server with shared records and a merge gate.

Install

curl -fsSL https://azimuth.sh/install | sh

This pipes a script from this site into your shell, and the file it installs is the tool that judges your code. Read the script first: site/install. It is short.

What the script does:

  • It reads the version that your repository pins in azimuth/project.toml. With no project file it takes the latest release.
  • It downloads the binary for your system from the releases on GitHub, over HTTPS only.
  • It compares the SHA-256 of the download with the sums file of that release, and installs nothing on a mismatch.
  • It writes only inside ~/.azimuth: the binary at ~/.azimuth/versions/<version>/azimuth, and a link at ~/.azimuth/bin/azimuth.
  • It never edits a shell profile.

So one step is yours. Add this line to your shell profile, once per machine:

export PATH="$HOME/.azimuth/bin:$PATH"

In GitHub Actions the script adds the folder to the path of the job itself, so a job needs the install line and nothing more.

Versions are kept side by side. In a repository that pins another version, run the same line again, and the link moves.

The sums file catches a broken download. It does not protect against somebody who controls the release. The binaries are not signed yet.

First steps

azimuth init
writes the project file, which pins the version, and the folder for local results.
azimuth skills install claude
writes the default process for an agent. codex works the same way.
azimuth lint
tells you whether the description is consistent with itself and with the code.
azimuth run
plans and runs the Checks that are owed.
azimuth status
tells you where the tree stands: which Requirements are proven, and what is missing for the others.
