# Deployment Claim Status design

## Authority
Implement decisions agreed with Dima in this conversation. Deployment is the assessment target. Runs preserve exact execution Subjects. Claim Review remains independently authored and assesses verification sufficiency, context completeness, mapping semantics and implementation. Claim Status is deterministic and is not another AI-authored conclusion. Historical claim-health records remain inspectable facts, not automatic authorization for the new applicability policy. Do not erase immutable records or rewrite historical release catalogs.

## Rules
- Require current Claim Review and required Check/Case bindings for confirmation; preserve routine-Claim policy explicitly rather than fabricating review acceptance.
- Same-deployment evidence requires exact Subject. Artifact evidence requires exact deployed component digest. Source evidence requires exact declared repository revisions/content fingerprints for the relevant component's build inputs. Do not infer applicability from shared model/branch/label or ignore extra/missing required source inputs.
- Build provenance and actual deployment reconciliation are framework relations, not product Checks. Trust configured project producers/observers; transport attribution is not cryptographic execution proof. Do not introduce mandatory PKI.
- Check metadata declares execution Subject kind, relevant component scope and context dependencies (explicit none allowed). No Applicable-to declaration: target is deployment. Existing binding/implementation identity mechanisms remain authoritative. Unspecified scope fails closed for cross-Subject use.
- Required satisfied coverage combines applicable current Run correction heads. A protocol-valid applicable violated Observation is adverse evidence; a definitive violated Claim requires the reviewed mapping's declared counterexample contribution. Execution/setup/transport error, skipped or incomplete reports are inconclusive; arbitrary test failure is not proof of a violated Claim. Missing/stale/rejected review blocks confirmation and does not hide adverse facts.
- Claim Status returns supported/violated/unresolved with human-facing Confirmed/Violated/Unresolved labels, exact dependency references, evaluated time, and specific missing/inapplicable/overdue reasons. Existing authored historical conclusions remain separate from computed status.
- Monitor references a Check, explicit deployment target binding, interval and freshness. Freshness uses observed time and trustworthy collection, not upload replay time. Missing future/skewed/expired or mixed-deployment observations cannot establish current support. Deployment observation freshness alone never renews Check evidence. Immutable source tests do not expire by arbitrary age.

## Context boundary
General endpoint/report: {format: azimuth-verification-context, version: 1, contexts: {name: {contract_revision: SHA256, values: object}}}. Context contracts declare allowed field names and types (string, boolean, nonnegative safe integer initially); reject extras, missing values and secret-bearing declarations. Application reports effective resolved values via private endpoint; never write application configuration from the contract. Caller/collector binds snapshots to actual instance/deployment and capture times, not self-asserted deployment identity. Configuration is startup-fixed initially; before/after snapshots must agree for the execution interval. Per-test overrides require separate captures and Run partitions; do not assign one job-wide context to heterogeneous tests. No supported inference from unknown or changing context.

## Public capture and reporting contract
Public test integrations run under ordinary dotnet test / playwright test. They do not contact ASS, hold its credentials, author Claim Review, or implement deployment applicability. Result adapters map explicit native test identities to declared Check/Case units under the exact launch and use the existing public Run builder/core validation. Reporter facts are not themselves Runs.

Shared report envelope: {format: azimuth-test-report, version: 1, framework: string, execution: string, started_at_ms: integer, finished_at_ms: integer, tests: [test]}. Each test: {id: string, attempt: integer starting at zero, outcome: passed|failed|skipped|timed-out|interrupted, started_at_ms: integer, finished_at_ms: integer, contexts: [{name: string, before: snapshot, after: snapshot}], diagnostics: [string]}. Snapshot: {captured_at_ms: integer, instance: string, report: verification-context-envelope}. Explicit no-context tests have an empty contexts array. Test identity mapping is supplied by the project; never use display-name guessing to infer Checks. Raw runner outputs remain artifacts, typed reporters preserve attempts and unsuccessful executions. Framework-specific extra native data may live in separate retained artifacts, not unknown report fields.

The xUnit fixture captures effective settings from the actual WebApplicationFactory/application instance supplied by the consumer, after overrides; its lifecycle API records tests/attempts and writes deterministic reports. The Playwright fixture captures from configured actual application endpoints and attaches facts to testInfo; reporter aggregates deterministic reports, preserving retries/workers/skips. Both provide typed configuration and documented minimal examples with synthetic applications. Context capture failure must not accidentally suppress test result retention.

## Publisher and adoption
Shared normalizer validates strict reports/mapping, completeness, context consistency, native launch selection and exact unit outcomes before returning a native bundle. A separate project-scoped publisher sends validated immutable Runs with idempotent/retry behavior; CI publication runs after test failures and cannot convert missing evidence to success. Existing Git release publication includes fresh source-bound Runs, not just retained local historical input. Avoid privileged execution of untrusted PR code; separate unprivileged execution and protected artifact verification/publication using existing CI boundaries.

## Persistence and rollout
Additive schema revision only, preserving v1/v2 rows and historical JSON wire identities. No production reset or Secret rotation. Dima explicitly authorized ASS deployment and restarting the consumer Azimuth workflow after verification. Prepare upgrade/rollback instructions, review data-preserving Terraform plans and apply only after gates pass. First prove end-to-end in synthetic and consumer environments. Production release acceptance/archive remains an owner boundary and is excluded.

## Commit-pinned CI distribution
Public registry publication is not a prerequisite. Consumer CI checks out an exact Azimuth Git commit, builds the CLI, packs the .NET harness into a temporary local NuGet feed and builds/packs the Playwright npm tarball. Test jobs consume artifacts built once from that exact commit; provenance records commit and artifact digests. Contracts come from the same checkout. No floating main or implicit dependency on an unpublished package version.

## Independent review disposition
Accepted design-review.md corrections. Per-Check deployment policy is structured metadata under a `Deployment:` JSON declaration in verification.md, retained in authored Check inputs (thus Check execution fingerprint) and exported on authority Check records as optional `deployment`. Historical Checks without this declaration remain inspectable but cannot silently support cross-Subject deployment inference. Policy fields: subject (source|artifact|deployment), components (nonempty stable component-ID array), contexts (array of context-contract fingerprints; empty explicit none), contribution (support|counterexample|both), monitor (null or {id, interval_seconds, freshness_seconds}). Existing bindings supply exact Case membership; contribution is per-Check initially and Claim Review pins the complete Check record including policy. Conflicting artifact producer input sets fail applicability. Compare exact complete source sets for selected component builds, not unrelated release sources.

Monitor currentness: correction heads first; then latest observed_at_ms per Monitor/Check/Case/deployment. Equal-time different outcomes are ambiguous; newer inconclusive replaces older support; historical adverse facts remain inspectable. Latest inconclusive/overdue is unresolved, not violated. Required monitoring uses per-observation freshness, max future skew five seconds, and no replay renewal. Known applicable counterexamples remain reported even if review is missing; confirmed always requires current review where non-routine policy requires it. No fabricated review for routine Claims.

Captures must cover every relevant ready live application instance, not one sample. Instance identity denotes process lifetime/configuration generation, never just reusable service name; before/after must match over the test interval. Trusted observer binds production capture to exact deployment/components/replicas with observed time and coverage. Untyped/self-asserted context provenance does not establish applicability.

## Integration refinement: exact execution activities

Real consumer integration demonstrated that complete semantic Checks span multiple fixture process lifetimes. A context capture therefore includes mandatory `activity`, null for deployment or whole-Run scope, otherwise an exact native activity ID. Capture bounds enclose the referenced activity; selected context fingerprints are keyed per activity. Only relied-on Check/Case unit attempts select these captures. Optional authored `units` fixes complete unit inventory; explicit `controls` identifies deliberate sensitivity unit/contract pairs, with no inferred bypass from mismatching settings and no positive support from controls alone. Optional `configuration_sources` includes explicitly named released configuration repositories beyond component build inputs. These fields participate in Check and Claim Review identity. All producers, relational schemas and validators change together before first publication of the capture contract.
