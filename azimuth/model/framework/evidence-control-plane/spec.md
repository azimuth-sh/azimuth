# Spec: framework/evidence-control-plane

## Claim: claims-own-governance-and-cases-own-addressability
Criticality: routine

Azimuth SHALL govern one product proposition as a Claim while retaining each normative
condition/outcome clause as an addressable Case within that Claim.

### Case: observable-cases-remain-addressable
- Event: a Claim needs several materially different conditions
- Required outcome: each condition remains an addressable Case within the Claim
- Additional condition or outcome: only the Claim owns criticality, production realization and total Judgment

## Claim: normative-text-remains-author-owned
Criticality: routine

Claim and Case bodies remain authored normative content whose meaning belongs to human and agent
review rather than interpretation by Azimuth core.

### Case: free-form-markdown-is-preserved

Azimuth accepts any non-empty free-form Markdown body, preserves its internal line structure and
includes it in the addressed Claim or Case fingerprint.

### Case: notation-has-no-implicit-semantics

Natural-language keywords, translations, tables, diagrams, code fences and domain notations do not
gain parser-defined meaning merely by appearing in a normative body.

## Claim: checks-bind-atomic-outcomes-to-cases
Criticality: routine

Azimuth SHALL treat a Check as a deliberately enrolled verification method whose atomic outcome
bears on Cases only through explicit Evidence Bindings.

### Case: one-check-supports-several-cases
- Event: one atomic Check outcome honestly bears on several Cases
- Required outcome: each Check-to-Case relationship is declared as a separate Evidence Binding

### Case: independent-outcomes-remain-separate
- Event: assertions can vary independently even though one native command executes them
- Required outcome: Azimuth represents them as separate Checks

## Claim: credibility-separates-method-from-applicability
Criticality: routine

Azimuth SHALL qualify shared Check-method credibility independently from the applicability of that
method to each Evidence Binding.

### Case: shared-method-does-not-repeat-review
- Event: one Check and common method context serve more than one Case
- Required outcome: one Method Qualification may support several Evidence Bindings
- Additional condition or outcome: every binding retains its own Applicability Decision

## Claim: runs-contain-subject-bound-execution
Criticality: routine

Azimuth SHALL represent a Run as a bounded execution envelope over an exact Subject that can
contain Check executions, Challenger executions or both.

### Case: check-execution-produces-observation
- Event: a Check reaches terminal outcomes within a Run
- Required outcome: the Run contains one satisfied, violated or inconclusive Observation for every selected Case

### Case: challenger-execution-produces-challenge-result
- Event: a Challenger reaches a terminal outcome within a Run
- Required outcome: the Run contains a Challenge Result rather than product evidence

## Claim: challenges-target-semantic-decisions
Criticality: routine

Azimuth SHALL target each Challenge Result at one exact Method Qualification, Applicability
Decision or Claim Judgment and SHALL propagate its impact through traceability without duplicating
the result.

### Case: direct-product-failure-remains-observation
- Event: an execution directly falsifies a product or operational Claim
- Required outcome: Azimuth records a violated Observation instead of reclassifying it as a Challenge Result

## Claim: core-owns-semantics-and-adapters-own-providers
Criticality: routine

Azimuth SHALL keep model traversal, semantic target selection and normalized-result validation in
core while configured adapters own provider-native selection, execution and report import.

### Case: adapter-reports-actual-selection
- Event: an adapter executes or imports a provider-native operation
- Required outcome: it reports actual selection with normalized outcomes
- Additional condition or outcome: it does not interpret the repository model independently
